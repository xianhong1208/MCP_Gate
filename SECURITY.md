# Security policy

## Report a vulnerability

Open a [GitHub security advisory](https://github.com/xianhong1208/MCP_Gate/security/advisories/new) or email the maintainer listed in `pyproject.toml`. Do not open a public issue for security problems. You will get an acknowledgement within a few days.

## Supported versions

Only the latest release on the `main` branch receives fixes.

## What MCP Gate protects and how

| Asset | Protection |
|---|---|
| RS256 signing private keys | Encrypted at rest with AES-256-GCM using `ENCRYPTION_KEY`; only public keys are ever served (`/.well-known/jwks.json`). After a rotation the old public key leaves the JWKS once nothing it signed can still be valid (the access-token lifetime, or longer while a PAT it signed is live), so rotating answers a key compromise: revoke the PATs signed before the rotation and the old key stops being accepted. |
| Stored secrets (service bearer tokens, container environment variables) | Same AES-256-GCM encryption. The console never returns them; environment values are write-only. |
| `ENCRYPTION_KEY`, `SESSION_SECRET_KEY` | Read from the environment, or generated on first start and written to `data/secrets.json` with mode `0600`. Rotating `ENCRYPTION_KEY` makes existing private keys and secrets unreadable. A hand-set value that is a placeholder, shorter than 32 characters or low in variety is warned about at every start and on the dashboard; a trivial one (placeholder, under 16 characters) is refused on a new install. |
| Owner password | bcrypt (12 rounds). Changing it ends every other console session of that account at once (the session records are deleted server-side). |
| Console session | HttpOnly cookie, `SameSite=Lax` by default, `Secure` when `SECURE_COOKIE=true`; 12-hour lifetime, 30-minute idle timeout in the UI. Each session has a server-side record (`admin_sessions`): logout deletes it, so a copied cookie stops working immediately; expired records are purged by the cleanup job. The cookie alone is not a session: every request must also send the per-session *binding* secret in `X-Session-Binding` (the WebSocket offers it as a subprotocol), which the console keeps in `localStorage` — scoped to its exact origin, port included — and which never travels in a cookie. See *Known limitations* for why. |
| Host names (DNS rebinding) | Requests are served only for the `OAUTH_ISSUER` host, `localhost` / `*.localhost`, IP addresses and names listed in `ALLOWED_HOSTS`; a rebound attacker domain gets 421 before it reaches setup, registration or discovery. Behind a trusted proxy `X-Forwarded-Host` is checked too, never instead of `Host`. |
| Console API (CSRF) | Every `POST` / `PUT` / `PATCH` / `DELETE` outside the OAuth protocol endpoints, plus the consent decision, must carry an `Origin` (or else `Referer`) that is the console's own origin, `OAUTH_ISSUER`, or listed in `cors.allowed_origins`; otherwise 403 `auth.csrf_origin_denied`. Requests with neither header (scripts, `curl`) are not from a web page and are let through to the normal session check. |
| Authorization codes | Stored as SHA-256 hashes, single use, 120-second lifetime, bound to client, redirect URI, PKCE challenge and resource. Reuse revokes every token derived from the code; a redemption that fails a check (PKCE verifier, client, redirect URI, resource) burns the code. |
| Refresh tokens | Rotated on every use; presenting a rotated token revokes the whole family. Their audience is MCP Gate's own token endpoint, so a resource server that checks `aud` (every `JWTVerifier` configured with its audience) refuses them as Bearer tokens; `MCPGateVerifier` also requires `token_use: access`. |
| Client secrets | Stored as SHA-256 hashes, compared in constant time, returned once at registration. |
| GitHub / Google sign-in | An existing account is matched by provider account id, or by email only when the provider reports that email as verified (Google `email_verified`; GitHub primary entry of `/user/emails`); the same applies to auto-creating accounts from `identity.allowed_emails`. |
| Redirect URIs | Exact-match against the registered list, except that a loopback redirect URI (`http://127.0.0.1/…`, `http://[::1]/…`, `http://localhost/…`) matches on any port (RFC 8252 §7.3, RFC 9700); scheme, host, path and query still match exactly. `http` is allowed only for loopback hosts. |

## Known limitations

- **Resource servers are explicit.** Only a confidential client registered in the console *and bound to one MCP server* may read the revocation feed, introspect other clients' tokens or report usage, and it only sees tokens whose audience is that server. Any other client can introspect only its own tokens.
- **Tokens verified offline stay valid after revocation until they expire — unless the server reads the revocation feed.** A resource server that verifies JWTs offline with a plain `JWTVerifier` never hears about a revocation, so it keeps accepting a revoked token until its `exp`:
  - an OAuth **access token**: at most the access-token lifetime (`OAUTH_ACCESS_EXPIRE_MINUTES`, 15 minutes by default);
  - a **personal access token**: its whole remaining lifetime — up to `oauth.pat_max_days` (365 days by default). Revoking a PAT in the console does **not** stop such a server from accepting it.

  The fix is the revocation feed, `POST /oauth/revoked`: bind a console-registered confidential client to the server (*OAuth Clients → Resource server…*) and have the server poll the feed with it. `MCPGateVerifier` from `examples/mcp_gate_hooks.py` does that (default every 15 s) and also reports usage, which shrinks the window to the poll interval for access tokens and PATs alike; use FastMCP's `IntrospectionTokenVerifier` where revocation must be instant. Until a server is wired to the feed, treat a leaked PAT for it as valid until it expires: keep PAT lifetimes short, or rotate the signing key (which stops every token it signed once the key leaves the JWKS, see above).
- **Single tenant.** Anyone who can sign in to the console is an administrator. Protect the console URL accordingly.
- **Single process.** The rate limiter counts requests in memory and the scheduler (expiry purges, audit retention, health checks) runs inside the server process. Run exactly one MCP Gate process: with several workers or replicas each one keeps its own counters, so the effective limit multiplies, and every scheduled job runs once per process. MCP Gate logs a warning at startup when `WEB_CONCURRENCY` or `UVICORN_WORKERS` is greater than 1.
- **Client IPs behind a proxy.** `X-Forwarded-For` / `X-Real-IP` are honoured only when the direct peer is listed in `security.trusted_proxies`, and `X-Forwarded-For` is read right to left, skipping trusted proxies. List every proxy hop you run there, or the audit log and the rate limiter see the proxy's address instead of the client's.
- **Dynamic client registration is open by default** (`OAUTH_DCR_AUTO_APPROVE=true`). Registering a client grants nothing by itself — the owner must approve every authorization on the consent screen — but set it to `false` if you want to review clients before they can even ask. A dynamically registered client can only use `authorization_code` and `refresh_token`: `client_credentials` (a token without consent) is reserved for confidential clients the owner registers in the console.
- **On `localhost`, every local port receives the console cookie.** Browsers scope cookies by host, not port, and treat every port of a host as the same site (even for `SameSite=Strict`), so while you are signed in to `http://localhost:4568` your browser also sends `mcp_session` to `http://localhost:<any port>`: an MCP client's OAuth loopback callback receives it the moment you approve that client, and so does a local dev server or any other process listening on loopback. MCP Gate makes that cookie useless on its own: every console request must also carry the session binding (above), which only a script running in the console's own origin can read, and `/oauth/authorize` never issues a code on the cookie alone (consent skipping happens on the consent page, which has the binding). What remains: the leaked cookie reveals the owner's email and user id (they are in the signed JWT), and a process on the same machine that can run script in the console's origin (XSS) or read the browser's profile directory is not stopped by this. For anything beyond a single-user workstation, serve the console under a dedicated host name (e.g. `https://mcp.example.com`, or `http://mcp-gate.localhost:4568` on one machine — browsers resolve `*.localhost` to loopback, but check that your MCP clients accept that `http` issuer) so its cookie is not shared with other local services, and use HTTPS with `SECURE_COOKIE=true`.
- **Plain HTTP is for local use only.** Deploy behind HTTPS (see [docs/deploy.md](docs/deploy.md)); the OAuth 2.1 specification requires it.
