# Changelog

All notable changes to MCP Gate (formerly MCP Center) are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- **Dependency audit in CI.** A new *Dependency audit* job runs `pip-audit` on the locked runtime dependencies and `npm audit` (production dependencies, high severity and above) on the console, so a dependency with a published vulnerability fails the build (#10).

### Security
- **First-run setup needs a one-time setup token** (#12). Until an owner exists, `POST /api/session/setup` created one for whoever called it first, with no credential, and MCP Gate listens on every interface by default — on a fresh install without `ADMIN_EMAIL` / `ADMIN_PASSWORD`, anyone on the network could become owner before the operator opened `/setup`. While no owner exists, MCP Gate now generates a token, prints it in the startup log and keeps it in `data/secrets.json` as `SETUP_TOKEN` (`MCP_GATE_SETUP_TOKEN` sets it instead); `/setup` asks for it (both languages), a missing or wrong token gets `403 auth.setup_token_invalid` and creates nothing, and the token is discarded once the owner exists. `ADMIN_EMAIL` / `ADMIN_PASSWORD` are unaffected.

## [1.2.0] — 2026-11-04

### Added
- **Client ID Metadata Documents** (draft-ietf-oauth-client-id-metadata-document-03; the registration method of the MCP authorization specification 2026-07-28). An MCP client may use the https URL of a JSON metadata document as its `client_id` without registering; the discovery metadata advertises `client_id_metadata_document_supported: true`. MCP Gate fetches the document at `/oauth/authorize` (and refreshes it at the token endpoint when the cached copy is stale), requires its `client_id` to equal the URL plus `client_name` and `redirect_uris`, refuses `client_secret` and shared-secret authentication, uses `private_key_jwt` when declared (with `jwks` or `jwks_uri`) and otherwise `none` + PKCE, and narrows `grant_types` to `authorization_code` / `refresh_token`. The fetch is SSRF-hardened: https only, public addresses only with the connection pinned to the checked address, no redirects, no proxy or cookies, 5 KB / 5 s, JSON media type. Documents are cached for their `max-age` within 1 minute–1 day; a failing URL is not refetched for 30 s; a transient failure at the token endpoint falls back to the stored copy, a `client_id` mismatch revokes the client's tokens, and changed redirect URIs, auth method or keys forget remembered consents. The client is stored as an OAuth client keyed by the URL (`created_via = cimd`), so tokens, consents, audit and revocation work unchanged; the consent screen names the URL's host and says the client is unverified; the OAuth Clients page labels it *Metadata document* (both languages). Configured under `oauth.cimd` (`OAUTH_CIMD_ENABLED`, `OAUTH_CIMD_AUTO_APPROVE`, `OAUTH_CIMD_ALLOWED_HOSTS`, `OAUTH_CIMD_PRIVATE_NETWORK_HOSTS`, plus timeout, size and cache bounds). Dynamic client registration keeps working alongside.
- **Revocation visibility.** A resource server's revocation-feed polls are recorded (`oauth_clients.revocation_polled_at`, migration `b8d0f2a4c6e9`; written at most every 30 s). The service page shows a *Revocation feed* row — wired with the last poll, stopped polling (no poll for 10 minutes), bound but never polled, or not wired ("revoked tokens stay valid until they expire") — and every revoke dialog (Tokens, token detail, service page) says whether the revocation reaches the token's server or how long it stays valid there. New endpoints `GET /api/oauth/services/{id}/revocation-feed` and `GET /api/oauth/revocation-feed?audience=`; the client record carries `revocation_polled_at`. Both languages. The revoke dialog no longer claims a token is "immediately invalidated" everywhere.
- **`scheduler` config section.** The purge interval and retention periods were hard-coded (`CleanupScheduler.configure()` was never called). `config.yaml` now has `scheduler.oauth_cleanup_hours` (6), `usage_retention_days` (30), `audit_retention_days` (90, env `AUDIT_RETENTION_DAYS`), `health_check_enabled` (true), `health_check_seconds` (30, env `HEALTH_CHECK_SECONDS`), `health_check_concurrency` (8), `health_check_timeout_seconds` (10) and `health_write_interval_minutes` (5); the defaults are the previous behaviour.
- **The OAuth protocol surface is audited.** Dynamic client registrations (`oauth_client_create`, actor `api`), consent decisions (`oauth_consent_approve` / `oauth_consent_deny`, with the client, resource and granted scopes), authorization-code replays (`oauth_code_replay`) and refresh-token reuse (`oauth_refresh_replay`, both with the number of tokens revoked), and failed client authentication on the token, revocation, introspection, feed and usage endpoints (`oauth_client_auth_failed`, with the client id the request claimed) now write audit entries. The audit log page labels and filters them in both languages.
- **Continuous integration.** `.github/workflows/ci.yml` runs on pushes and pull requests to `dev` and `main`: the backend suite and ruff on SQLite, the same suite on PostgreSQL 16, the frontend lint / tests / build with a check that the committed `static/web` matches the build, and a build and smoke test of the `mcp-runtime` image as its runtime user.
- **The test suite runs on PostgreSQL.** Set `TEST_DATABASE_URL` to a throwaway database: the schema is rebuilt once per session and the tables are truncated before each test. SQLite stays the default.
- **Console UI for resource-server binding and key retirement.** *OAuth Clients → Register trusted client* has a **Resource server for** picker for confidential clients (`resource_service_id`), and each console-registered confidential client has a **Resource server…** action to bind, change or remove it (`PUT /api/oauth/clients/{id}/resource-server`); the client list names the bound server. The signing-key list shows whether a retired key is still published in the JWKS, and the audit log labels the new `oauth_client_bind` action (en + zh-TW).
- **Schema drift test.** `tests/test_schema_drift.py` migrates an empty database to head (and back down and up again) and compares it with the models using Alembic's autogenerate comparison.

### Changed
- **`client_id` columns are 255 characters** (were 64) in `oauth_clients`, authorization requests, codes, tokens, consents and token events, and the audit log's `resource_id` / `actor_id` are 255 (were 128), to hold a metadata-document URL (migration `c9d1e3f5a7b9`, which also adds `oauth_clients.metadata_fetched_at`). Downgrading removes clients whose id is longer than 64 characters (their tokens are kept as history).
- **The console's client endpoints take any client id** (`/api/oauth/clients/{client_id:path}`), so a URL-shaped id can be read, approved, revoked and deleted. The unused-client purge (`dcr_unused_client_days`) also removes active metadata-document clients that never obtained a token; a revoked one is kept, since it is how a URL stays blocked.
- **`/oauth/authorize` has its own rate limit** in the shipped `config.yaml` (60 per minute per IP), since it may fetch a metadata document.
- **A `jwks_uri` on loopback is allowed only for console-registered clients** (`manual` / `system`), named explicitly instead of "anything not dynamically registered", so a metadata-document client can never aim the key fetch at this machine.
- **OAuth access tokens now last 15 minutes by default (was 60).** `OAUTH_ACCESS_EXPIRE_MINUTES` / `oauth.access_expire_minutes` still sets it. A server that verifies offline without the revocation feed accepts a revoked access token until it expires, so a shorter lifetime shortens that window; MCP clients renew with their refresh token (rotation is unchanged). Personal access tokens (their own lifetime, up to `pat_max_days`), refresh tokens (30 days) and the console's scanner tokens are unaffected. A retired signing key now leaves the JWKS sooner, since that delay follows the access-token lifetime. **Set `OAUTH_ACCESS_EXPIRE_MINUTES=60` to keep the old behaviour.**
- **Loopback redirect URIs match on any port** — `http://127.0.0.1`, `http://[::1]` and `http://localhost` (RFC 8252 §7.3; RFC 9700 §2.1 / §4.1.3). CLI and desktop MCP clients register e.g. `http://localhost:<port>/callback` and listen on whatever port is free each run. Scheme, host, path and query still match exactly; `localhost` and `127.0.0.1` are not interchangeable; every other redirect URI is an exact match.
- **`SECURITY.md` no longer understates the offline revocation delay.** It said a revoked token stays valid at an offline-verifying server for "60 minutes by default"; that is only true of OAuth access tokens. A personal access token stays valid there for its whole remaining lifetime (up to `pat_max_days`, 365 days by default) unless the server polls the revocation feed (`POST /oauth/revoked`). The README (both languages) says the same.
- **`ROADMAP.md` is current:** `private_key_jwt` client authentication shipped in 1.1.0 and is listed as done instead of planned.
- **SQLite connections set `busy_timeout=5000` and `synchronous=NORMAL` explicitly** (with WAL, as before). A writer waits up to 5 s for another instead of failing with "database is locked", and WAL commits need far fewer fsyncs; only a power loss (not an application crash) can drop the last commits. PostgreSQL is unchanged.
- **Renamed MCP Center to MCP Gate.** The console, docs, package (`mcp-gate`), repository (`MCP_Gate`) and code identifiers follow the new name: `examples/mcp_center_hooks.py` is now `examples/mcp_gate_hooks.py` with `MCPGateVerifier`, and the exception base classes are `MCPGateError` / `MCPGateHTTPException`. The environment variables are now `MCP_GATE_CONFIG` and `MCP_GATE_SECRETS_FILE`; the old `MCP_CENTER_*` names are still read as a fallback.
- Identifiers that live in existing data keep their old spelling so nothing has to migrate: the built-in client ids `mcp-center-console` / `mcp-center-scanner` (stored in the database and carried in issued tokens) and the default database `data/mcp_center.db`. Tokens already issued stay valid — the issuer is the URL, not the name.

### Fixed
- **The bring-your-own deploy preview shows the right endpoint.** It showed `127.0.0.1:<port>/sse`, but the supergateway bridge serves Streamable HTTP on `/mcp` (the path the created service gets). The preview and the orchestrator docstring now say `/mcp`, and a frontend test pins the preview to the backend's `STDIO_HTTP_PATH`.
- **Health rounds run concurrently and write less.** Services were checked one after another, so one slow or hanging server delayed the whole round (and every later one). Checks now run concurrently, at most 8 at a time, and each is cut off after 10 s (stored as an `error` with "health check timed out"). A health row is written only when the status changes, while a failure streak is still counting towards `offline`, or when the stored check is older than 5 minutes — not for every service every 30 s. "Last checked" can therefore be up to 5 minutes old for a steady service.
- **The rate limiter no longer grows without bound.** Every client IP left its counter keys (and expired blocks) in memory forever — `SlidingWindowCounter.cleanup()` existed but nothing called it, and reading the stats for a response created keys too. Idle keys are now swept at most once a minute from the request path, so memory follows the clients seen in the last hour.
- **`oauth_tokens.parent_jti` is indexed** (migration `a7c9e1f3b5d7`). Family revocation on a code replay or refresh-token reuse filters on it, and scanned the whole token table.
- **Startup no longer waits for managed servers.** Reconciling managed servers at startup restarted every dead one in turn (a stdio cold start may take up to 300 s), and the server did not answer — not even `/.well-known/*` or `/oauth/token` — until all of them were up. Reconcile now runs in a background thread after startup.
- **A managed server's service can no longer be deleted from the Services page while its instance exists.** `DELETE /api/services/{id}` removed only the row and left the container or process running, unregistered and without OAuth in front of it. It now answers 409 `service.managed_use_uninstall` naming the instance (shown as a translated error in both languages); Marketplace → Uninstall stops the instance and removes the service. A service whose instance is already gone can still be deleted. (known #22)
- **`POST /api/system/cleanup/run` reports failed jobs.** Each clean-up job caught its own error and returned 0, so a failing purge was answered with "Cleanup completed". The manual run now answers 500 `system.cleanup_failed` naming the failed jobs (their count is `null`, the others are still reported) and audits the run as a failure; scheduled runs still log and carry on. (known #23)
- **One failing service no longer ends the scheduled health round.** A failed write for one service (e.g. a `DataError` on PostgreSQL) left the session needing a rollback, so every later service failed too and the round stopped; "Check all" had the same problem. Each service is now rolled back on its own, and the counters count a status only once it is stored.
- **One bad host or server no longer fails the whole discovery scan.** A host resolving to a blocked address (link-local / cloud metadata) used to turn the scan into a 500 for every host; it is now skipped and listed in `skipped_hosts` (`discovery.address_blocked`). Auto-register is all-or-nothing per server (service, tools and health stamp, undone if any step fails), and a server that cannot be registered gets a `register_error` on its row while the others still register; previously one failure answered 500 and left earlier and half-registered services behind. The scan dialog shows both, in English and Traditional Chinese. (known #16, #20)
- **Works with fastmcp 4 / mcp 2 clients.** The integration snippet, README and examples pass the issuer to `RemoteAuthProvider(authorization_servers=...)` as a plain string; `AnyHttpUrl` added a trailing slash that mcp 2 clients reject as an issuer mismatch. The dev/interop dependency moves to fastmcp 4, and troubleshooting covers the error. (#37)
- **"Refresh from Server" no longer wipes the stored tools when the server cannot be read.** A non-200, transport error or malformed `tools/list` reply now answers 502 and keeps the existing tools; only a valid empty `tools` result clears them. A scan that verifies a server but cannot list its tools still registers it, without tools. (#34)
- **Discovery scans are bounded.** Ports must be 1–65535 and a port range must satisfy `1 <= start <= end <= 65535` (a start of 0 or a reversed range used to be silently ignored); at least one host and one port are required, and one request may probe at most 65,536 host × port combinations. Rejections are 422s with `discovery.*` error codes the console shows in both languages. (#34)
- **Health checks keep the description you wrote.** The scheduled and manual health checks used to overwrite every service description with the server's `serverInfo`; they now fill it only while it is empty or still generated (the scan placeholder or the old health-check text). (#34)
- **A reachable server without auth and without tools is no longer reported as "requires auth".** The scan now decides from the verification result rather than from whether any tools came back. (#34)
- Stdlib logging (uvicorn, APScheduler, SQLAlchemy and modules using `logging.getLogger`) is routed into loguru and reaches the log files; uvicorn's access log is off because the request-logging middleware already records every request. (#35)
- bcrypt hashing and verification for setup, login and password change run in a worker thread instead of blocking the event loop. (#35)
- Scheduled purges of expired OAuth data, token events and old audit logs write a system audit entry when they delete anything. (#35)
- Downgrading migrations `4b2c9d7e1f03` and `1ee09c99d84d` no longer fails on data the newer schema allows: authorization requests/codes without PKCE and tokens of deleted clients are removed first. `oauth_clients.require_pkce` declares the same server default in the model as in the migration. (#35)
- The single-process requirement (in-memory rate limiter, in-process scheduler) is documented in `SECURITY.md` and `docs/deploy.md`, and startup warns when `WEB_CONCURRENCY` or `UVICORN_WORKERS` is greater than 1. (#35)
- **Over-long input is refused with a readable error instead of a 500 on PostgreSQL.** SQLite ignores `VARCHAR(n)`, PostgreSQL rejects the row. Service name, host, tags, audience and allowed scopes; the owner's email and display name; scope names and descriptions; bring-your-own and managed instance names; and the scan's host and service name now answer `validation.too_long` naming the field and its limit (shown in both console languages). Dynamic client registration refuses over-long `client_uri`, `logo_uri`, `software_id`, `scope`, `default_resource`, `jwks_uri` and redirect URIs with `invalid_client_metadata` / `invalid_redirect_uri`, and `/oauth/authorize` refuses an over-long `state` or `code_challenge` with `invalid_request`.
- **Text MCP Gate relays is shortened rather than failing the request.** Health-check error messages from the remote server are cut to 512 characters; audit entries clip the failed-login email, User-Agent and other bounded fields; a long GitHub / Google display name is shortened; and a scanned server's name is cut to fit.
- **One bad tool no longer fails "Refresh from Server" or a scan.** Tools with a missing, blank or over-long (more than 128 characters) name are skipped and repeated names keep their first entry, instead of a 500 on PostgreSQL that left a scanned service half-registered.
- **Static bearer tokens of any realistic length.** `services.auth_token_encrypted` is now `TEXT` (migration `d4e6f8a0b2c3`): once encrypted, the old `VARCHAR(1024)` held only about 740 bytes, less than a typical JWT. Tokens over 8,192 characters are refused.
- **The revocation feed and usage reports use real unix time on hosts outside UTC.** `revoked_at`, `exp`, `now`, `since` and `last_seen` treated stored local times as UTC, shifting them by the host's UTC offset.
- **Migrations work with a percent-encoded `DATABASE_URL`.** A password containing e.g. `%40` made Alembic's config parser fail, so startup migrations could not run.
- **`mcp-runtime` image: `uvx` works as the runtime user and `python` exists.** uv was installed under `/root/.local/bin`, which the unprivileged `mcp` user cannot reach, so every `uvx` bring-your-own server failed to start; `python` (on the bring-your-own allow-list) was missing. uv now comes from the official image into `/usr/local/bin`, `python-is-python3` is installed, and uv and supergateway versions are pinned.

### Security
- **The consent screen shows where the browser is sent back to, and warns about loopback-only clients.** The redirect host moved from the small footer into the request summary, and when every redirect URI the client registered is on this machine (`localhost`, `127.0.0.1`, `[::1]`) a warning asks the owner to approve only an app they just started themselves, since any local program on that port receives the code (`redirect_loopback_only` in `GET /oauth/authorize/requests/{id}`; both languages). The page already could not be framed (`frame-ancestors 'none'`, `X-Frame-Options: DENY`); a test now pins that for `/consent`.
- **PKCE downgrade is refused (RFC 9700 §4.8.2).** A token request carrying `code_verifier` for a code whose authorization request had no `code_challenge` (only possible for classic console clients with `require_pkce=false`) used to have the verifier ignored; it is now `invalid_grant` and burns the code.
- **An authorization code or refresh token can be redeemed only once, even concurrently.** Redemption checked `used_at` / `revoked_at` and then set it, so two simultaneous requests with the same code (or refresh token) could both get tokens. The claim is now one conditional `UPDATE … WHERE used_at IS NULL` (`revoked_at IS NULL` for rotation), committed together with the tokens it pays for; the request that loses is treated as a replay — `invalid_grant`, and every token of the grant, including the winner's, is revoked. Tested with two threads on SQLite and PostgreSQL.
- **Cross-site request forgery against the console is refused.** `SameSite=Lax` does not separate pages on other ports of the same host (or sibling subdomains), and body-less POSTs need no CORS preflight, so a page on any other `localhost` port could rotate the signing keys, revoke tokens, start managed servers or approve a consent with the owner's cookie. Every `POST` / `PUT` / `PATCH` / `DELETE` outside `/oauth/*` and `/.well-known/*`, and the consent decision, now needs an `Origin` (or else `Referer`) that is the console's own origin, `OAUTH_ISSUER` or an entry in `cors.allowed_origins`; anything else gets 403 `auth.csrf_origin_denied`. Requests without either header (not from a web page) and Bearer-only requests without the cookie are unaffected.
- **Foreign host names are refused (DNS rebinding).** A page on an attacker's domain re-pointed at 127.0.0.1 could use MCP Gate's unauthenticated surface as if it were same-origin: run first-time setup on a fresh install, register clients, read discovery. Requests are now served only when `Host` is the `OAUTH_ISSUER` host, `localhost` / `*.localhost`, an IP address, or listed in the new `ALLOWED_HOSTS` (`security.allowed_hosts`; exact names, `*.suffix`, or `*` to disable); others get 421 `http.host_not_allowed` (WebSocket: close 1008) and one log warning per name. Behind a trusted proxy `X-Forwarded-Host` must pass as well, but never replaces `Host`. `/health` is always served. Such hosts are refused before the issuer-mismatch check, so they no longer appear on the dashboard as a suggested `OAUTH_ISSUER`. **If other containers or an internal DNS alias reach MCP Gate by a name that is not the issuer's, add it to `ALLOWED_HOSTS`.**
- **The Vite dev port no longer has credentialed access to the admin API (H-15).** `http://localhost:5173` was in the default and shipped `cors.allowed_origins` with `allow_credentials: true`, so any app served on Vite's default port could read and drive the console API from the owner's browser. The default is now empty (the console is same-origin and needs no CORS); extra origins are opted in with `CORS_ALLOWED_ORIGINS` (comma-separated) or a YAML list. The Vite dev server rewrites its own Origin to the backend's while proxying, so `npm run dev` keeps working without an entry. **If you relied on `:5173` or `:4568` being listed, set `CORS_ALLOWED_ORIGINS`.**
- **Weak `SESSION_SECRET_KEY` / `ENCRYPTION_KEY` values are reported.** A hand-set value that is a known placeholder (`changeme`, `secret`, …), shorter than 32 characters or made of fewer than 10 distinct characters is logged as a warning at every start and shown as a dashboard banner (`weak_secrets` on `GET /api/oauth/overview`). A *trivial* value (placeholder, under 16 characters, under 6 distinct characters) is refused only on a new install (no signing key in the database yet, so nothing is encrypted with it); existing installs keep starting, because rotating `ENCRYPTION_KEY` there makes the stored private keys unreadable. Generated values are unaffected.
- **First-time setup creates exactly one owner (H-05).** Concurrent `POST /api/session/setup` requests could all pass the "no account yet" check during the bcrypt hashing and each create an owner (4 of 4 did in a test), leaving extra admin logins the console never shows. The owner now takes a unique `admin_users.owner_slot` (migration `f6a8b0c2d4e6`; on existing installs the earliest account gets it), so the database lets exactly one request win on SQLite and PostgreSQL alike; the others get 409 `auth.setup_already_done`. The `ADMIN_EMAIL` bootstrap takes the same slot.
- **GitHub / Google sign-in can no longer take over an account through an unverified email (H-03).** Linking a provider account to an existing console account by email (and auto-creating an allow-listed one) now requires the provider to have verified that email: Google's `email_verified` must be true (the string `"true"` counts, `"false"` no longer does), and GitHub's email now always comes from the primary entry of `/user/emails` with its `verified` flag — the public profile email is never trusted. An unverified match is refused with `auth.external_email_unverified` and audited as a failed login; a successful link is recorded in the login audit entry. A non-ASCII or over-long `state` on the provider callback is a failed login instead of a 500.
- **A leaked console cookie is no longer a session (H-04).** Browsers send cookies to every port of a host, so on a `localhost` deployment an MCP client's OAuth loopback callback (`http://localhost:<port>/cb`) received the owner's `mcp_session` cookie when the consent was approved, and could replay it for a 12-hour admin session. Every console request now also needs the per-session *binding* secret in the `X-Session-Binding` header (the `/ws/services` WebSocket offers it as the subprotocol `mcp-gate.v1.binding.<value>` and is answered with `mcp-gate.v1`). The secret is returned in the login / setup / password-change response body (`session_binding`), or in the `#mcp_sb=` fragment after a GitHub / Google login, and the console keeps it in `localStorage`, which is scoped to its exact origin; the cookie JWT carries only its hash. A cookie without the binding gets 401 `auth.session_binding_invalid` and cannot even log the owner out. `/oauth/authorize` no longer issues a code itself when consent may be skipped (that 302 handed the code to whoever replayed a leaked cookie); it always redirects to `/consent`, which approves automatically when `can_skip` is true. Scripts that call the console API with a session cookie or Bearer session token must send `X-Session-Binding` too.
- **Logout and password changes end sessions server-side.** Console sessions now have a server-side record (new table `admin_sessions`, migration `e5f7a9b1c3d5`). Logout deletes it, so a copied cookie stops working at once instead of staying valid for 12 hours, and logout is written to the audit log (`admin_logout`). A password change deletes every other session of the account, including one issued within the same second (the old check compared whole-second `iat`), and no longer compares wall-clock times at all: restarting with a TZ further west after a password change used to make every new session look revoked (login 200, then `/me` 401). Session expiry is kept in UTC. Logout now deletes the cookie with the same `Secure` / `SameSite` attributes it was set with, so `COOKIE_SAMESITE=none` deployments no longer keep the cookie. **Upgrading signs everyone out once**: cookies issued by earlier versions have no record.
- **The startup banner no longer prints the database password.** `Database:` showed `DATABASE_URL` as configured, so a PostgreSQL password ended up on stdout and in `logs/app_*.log`. The banner masks it (`postgresql://app:***@db/mcp`, also `?password=`), and so does the "Failed to initialize database" error. (N1)
- **Process-runtime servers listen on 127.0.0.1 only.** Under `MCP_RUNTIME=process` the supergateway bridge listened on every interface (supergateway 3.x has no bind option), so a managed server answered unauthenticated MCP calls on the host's LAN address although the console says it is bound to 127.0.0.1. The runtime now passes `--host 127.0.0.1` (supergateway ≥ 4.2.0) and preloads a small Node module through `NODE_OPTIONS` that pins every wildcard `listen()` to 127.0.0.1, which covers older versions too (verified with 3.4.3). The Docker runtime already published on 127.0.0.1 and is unchanged. (N2)
- `GET /api/system/version` returns only the app version without a session; build, Python version and OS need a login. (H-18)
- **The consent and OAuth Clients pages no longer load a client's `logo_uri`** (fetching it told whoever registered the client when, and from which IP, the owner opened the page), and `client_uri` is a link only when it is an absolute `http(s)` URL; anything else, such as a stored `javascript:` URI, is shown as plain text. This holds for clients registered before registration-time URI validation. (H-16)
- **The issuer-mismatch list can no longer be filled by arbitrary `Host` headers.** Every distinct host that reached the OAuth surface was kept forever (301 forged hosts gave a 1.26 MB dashboard payload) and a host named by an attacker was logged with "set OAUTH_ISSUER to …". Only valid `http(s)://host[:port]` values are recorded, at most 20 (internet-named hosts evicted first), each forgotten 24 h after last seen. The advice is given only when the request came from a loopback/private address or a trusted proxy; hosts named by internet clients are flagged `plausible: false`, marked on the dashboard, and their warnings are capped at 20 an hour. (H-10)
- **BYO launch secrets are masked.** Credentials pasted into a BYO definition's args (`--api-key=…`, `--token …`, `API_KEY=…`, a password in a URL's userinfo) were returned by `GET /api/byo-mcp` and written verbatim into the audit log. API responses and audit details now show `****` for them; the stored definition keeps the real values for launching. A flag or env name counts as sensitive when it contains key, token, secret, password/passwd/pwd, auth, credential or private. (known #8)
- **Copy-paste snippets are quoted.** A scanned MCP server chooses its own `serverInfo.name`, which became the service name and was pasted verbatim into `claude mcp add --transport http <name> <url>` (a name like `pwn;touch${IFS}X;#` ran a command in the admin's shell) and into the Python snippets. Shell snippets now quote every argument and use a slug (`[A-Za-z0-9_-]`) as the Claude Code / `mcpServers` name, Python snippets embed values as string literals, and names adopted from `serverInfo` keep only `[A-Za-z0-9._-]`. The token-created page builds its command the same way. (H-08)
- **A burst of unauthenticated requests can no longer freeze the server.** About 17 concurrent `GET /.well-known/jwks.json` used to exhaust the connection pool and block the event loop on the next checkout (the connections already out could only be returned by that same loop), stalling every request for minutes. JWKS and authorization server metadata are now served from memory. They are invalidated when a signing key, a scope, a service or a token revocation is written; the JWKS also expires at the next scheduled key retirement and after 30 s at most, so a retired key still leaves it on time (metadata: 60 s safety TTL), and the remaining OAuth protocol endpoints and the session dependencies run their database work in the threadpool. (H-06)
- **Dependencies with known advisories upgraded** (`pip-audit` / `npm audit --omit=dev` now clean): pyjwt 2.15, cryptography 50, starlette 1.10 / fastapi 0.162, aiohttp 3.14, urllib3 2.8, anyio, multidict, idna, certifi, python-dotenv, mako, pygments, dnspython; dev-only fastmcp 3.4.10 / mcp 1.30 / authlib / joserfc. The console moves to react-router 7, which fixes open-redirect advisories in v6. Minimum versions of pyjwt, cryptography and aiohttp are raised in `pyproject.toml`. (#32)
- **Outbound fetches can no longer be steered at internal addresses.** The discovery scanner, health checks and tools refresh never follow HTTP redirects, and a host that does not resolve is refused instead of being handed to the HTTP client by name; the cloud metadata addresses `fd00:ec2::254` and `100.100.100.200` are blocked too (loopback and private ranges stay scannable). The `jwks_uri` fetch connects to the exact address that passed the check (Host header, TLS SNI and certificate verification keep the hostname), accepts only globally routable addresses, ignores proxy environment variables, and refetches for an unknown `kid` at most once a minute per `jwks_uri`. Client authentication on the token, revocation, introspection and feed endpoints runs off the event loop. (#33)
- **Client IPs can no longer be forged.** One resolver now feeds the audit log, request logging, OAuth token events, the rate limiter and the issuer check: `X-Forwarded-For` / `X-Real-IP` count only when the direct peer is in `security.trusted_proxies`, and `X-Forwarded-For` is read right to left, skipping trusted proxies (previously the audit log and request log trusted the headers from anyone, the rate limiter took the client-controlled leftmost entry, and OAuth token events ignored proxies altogether). (#35)
- Security headers are now added by the outermost middleware, so rate-limit 429s, CORS preflight responses and unhandled 500s carry them too. (#35)
- **Managed servers keep their port across restarts.** A process reuses the port it already has whenever nothing else holds it (its own leftover container is removed first) instead of taking the lowest free port and silently moving its Service; when the port truly cannot be reused it is moved with a warning in the log and in `last_error`, and a manually chosen port that is in use fails the start. Ports are reserved in the database at allocation time so concurrent starts cannot collide. (#36)
- **Readiness means an MCP answer, not an open port.** After the port opens, start polls an MCP `initialize` on `/mcp` until the existing start timeout (still 300 s for stdio cold starts) and fails the start if it never gets a JSON-RPC response — Docker's port proxy accepts connections before the server is up. (#36)
- **Stop failures are no longer swallowed.** The Docker and process runtimes treat only "already gone" as success; any other failure leaves the process in `stop_failed` with `last_error` set, `POST /api/managed/{id}/stop` reports it, and uninstall aborts without deleting the record while the instance may still be running. (#36)
- **Failed deployments keep their logs.** The last 50 log lines are copied into `last_error` before the failed container or process is removed, and any failure after a successful launch (e.g. registering the Service) now tears the instance down instead of leaking it. (#36)
- **One slow start no longer blocks every managed server.** Locking is per process (plus a short global lock for shared state and port allocation). Updating env vars stops, writes and restarts as one locked operation, marks a failed restart `failed` and audits it, and now works for bring-your-own servers too. (#36)
- **Docker unavailable returns 503 `managed.runtime_unavailable`** instead of a generic 500 from start, stop, env-var updates and uninstall. (#36)
- **Catalog entries must declare `transport: http`.** Any other value is rejected when the catalog is loaded (the file is skipped with the reason logged) rather than failing at start time. (#36)
- **Dynamically registered clients can no longer use `client_credentials`.** Anonymous registration used to accept the grant, which gave anyone who could reach MCP Gate a consent-free token for every registered server. `POST /oauth/register` now rejects it (whatever `OAUTH_DCR_AUTO_APPROVE` says) and the token endpoint refuses it for any client not registered in the console, including DCR clients stored by earlier releases. A DCR client also may not point a `private_key_jwt` `jwks_uri` at loopback, even on a plain-http development issuer.
- **Resource servers must be bound to a server.** Any confidential client — including one anyone could register anonymously — used to be trusted as a resource server: it could read the whole revocation feed, introspect any token (including the owner's email) and forge usage counts. Now only a console-registered confidential client bound to one MCP server (`resource_service_id` on `POST /api/oauth/clients`, or `PUT /api/oauth/clients/{id}/resource-server`; stored as `oauth_clients.resource_audience`, migration `e5f7a9b1c3d4`) may do so, and only for access tokens whose audience is that server; refresh tokens are never shown to it. **Breaking:** an `MCPGateVerifier` / `IntrospectionTokenVerifier` client created before this release must be bound before its feed, introspection and usage calls work again. Usage reports reject counts outside 1–1,000,000 and `last_seen` more than five minutes in the future with `invalid_request` (a huge or infinite count used to answer 500).
- **Refresh tokens can no longer be used as Bearer access tokens.** They carried the same `iss`/`aud`/`scope` as access tokens, so a server verifying offline accepted them for their full 30 days. Refresh tokens now name MCP Gate's token endpoint (`<issuer>/oauth/token`) as their audience, so the generated `JWTVerifier` snippet refuses them, and `MCPGateVerifier` additionally rejects anything whose `token_use` is not `access`. Revoked refresh tokens (other than routine rotation) are listed in `/oauth/revoked`. Refresh tokens issued by earlier releases still carry the server's audience until they are next rotated or expire; rotating the signing key after upgrading retires them (see key retirement below). Clients treat refresh tokens as opaque, so nothing changes for them; rotation and reuse detection are unchanged.
- **Deleting an OAuth client revokes its tokens** (reason `client_deleted`, listed in the revocation feed) before keeping them as history; previously its access and refresh tokens stayed valid until expiry.
- **A disabled server gets no new tokens from any grant.** The refresh grant and the authorization-code exchange now re-check that the token's server is still active (and that the user who consented is still active) and answer `invalid_grant` otherwise; a refused refresh does not rotate the token, so re-enabling the server makes it usable again. Personal access tokens can no longer be issued for a disabled server.
- **Dynamic registration is bounded and type-checked.** `/oauth/register` bodies are capped at 64 KiB (413), `redirect_uris` at 20 entries (validated whenever present, not only with `authorization_code`), `response_types` at 5 short strings; a non-string `client_name`, `grant_types` entry or auth method is an `invalid_client_metadata` 400 instead of a 500. The token, revocation, introspection and feed endpoints cap form bodies at 64 KiB (usage reports at 512 KiB), and over-long `scope` / `resource` parameters on `/oauth/authorize` and `/oauth/token` are refused. Building on the column-length checks above, a 20 MB `client_uri` no longer lands in the database.
- **`client_uri`, `logo_uri`, `tos_uri` and `policy_uri` must be web URLs** — `https`, or `http` to `localhost` / loopback. `javascript:`, `data:`, `file:` and plain-http remote URLs are refused at registration (DCR and console), so the consent screen can no longer be handed a script URL or a tracking pixel on another host.
- **Dynamically registered clients that never obtained a token are purged** 30 days after registration by the OAuth cleanup job (`oauth.dcr_unused_client_days`, `0` disables it). Clients that completed a flow, console clients and built-in clients are never touched.
- `GET /api/oauth/activity` (`at`) and the consent-request details (`expires_at`) now carry their UTC offset like every other console timestamp; they were naive local times that a browser in another time zone misread.
- **Rotated signing keys are retired from the JWKS.** Every key ever created used to stay published forever, so a leaked old private key could mint tokens resource servers accept indefinitely. A rotated-out key now stays in `/.well-known/jwks.json` for the access-token lifetime plus 5 minutes (`oauth.retired_key_publish_minutes`), and longer only while a live access token or PAT it signed is still recorded; introspection treats tokens signed by an unpublished key as inactive. MCP Gate keeps the key to verify the refresh tokens it signed, so clients refresh without noticing. `GET /api/oauth/keys` reports `published` per key.
- **A failed code redemption burns the authorization code** (OAuth 2.1): a wrong PKCE verifier, client, redirect URI or resource used to leave the code redeemable for the rest of its 120 s.

## [1.0.0] — 2026-09-01

First public release. MCP Center is an OAuth 2.1 authorization server and management console for Model Context Protocol servers.

### Authorization server
- RS256 signing keys with JWKS publishing and rotation; private keys encrypted at rest.
- Authorization server metadata (RFC 8414), dynamic client registration (RFC 7591), authorization code + PKCE (S256), refresh-token rotation with replay detection, revocation (RFC 7009), introspection (RFC 7662), resource indicators (RFC 8707), `iss` in authorization responses (RFC 9207).
- Consent screen with remembered decisions per client and server; trusted (manually registered) clients skip it.
- Personal access tokens minted from the console.
- Introspection is scoped: public clients may only introspect their own tokens; confidential clients (resource servers) may introspect any token.
- Classic-client compatibility for manually registered confidential clients: PKCE may be waived and a default resource assumed, so platforms with a plain client_id / client_secret OAuth module can sign in (migration `4b2c9d7e1f03`).

### Console
- Email/password sign-in with a first-run setup wizard; pluggable GitHub and Google sign-in (experimental).
- Dashboard, MCP server registry with health monitoring and tool sync, token management, OAuth client management, scope registry, key rotation, audit log.
- Marketplace and bring-your-own MCP server deployment through Docker.
- Network scan recognises OAuth-protected servers by their `WWW-Authenticate: Bearer` challenge and, for servers that trust this MCP Center, mints a scanner token to read their name and tools; no HTTPS retry against ports that already answered HTTP.
- Design system "Navy Trust" (dark-first, Fira Sans / Fira Code), app-shell layout with global search.

### Platform
- SQLite by default, PostgreSQL optional; UUID primary keys through SQLAlchemy's portable `Uuid` type.
- Secrets generated on first start and stored in `data/secrets.json`.
- Alembic migrations (`8813dec38e2b` initial schema, `1ee09c99d84d` keeps token history when a client is deleted).
- Verified against FastMCP 3.4 with an end-to-end interop test suite.

### Scope
- Tokens are standard RS256 JWTs that resource servers verify offline against the published JWKS; there is no opaque token format and no verification callback.
- The console is single-tenant: everyone who can sign in is an administrator, with no roles or per-service user membership (see `SECURITY.md`).
